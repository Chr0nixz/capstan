# M2 contracts and implementation boundary

> 2026-10-20 · Input/resource contracts frozen from the [A1 engineering references](baselines/M2/raw/2026-10-18-a1/README.md) before product candidate measurement. Core bidirectional partial continuation now has an explicit retry/session contract; recursive deletion and concurrent exit draining are defined below. Current gate status: [M2-A](M2-A.md). The remaining feature workflows have implementations; full B quantitative and desktop acceptance remain outstanding.
> Authority: [M2.md](M2.md), especially §4–6. `PLAN.md` remains unchanged.

## Approved subsystem pool, 2026-10-20

The maintainer approved up to three SFTP subsystems per authenticated SSH
connection in the current conversation. This replaces M2's earlier single
subsystem restriction and is an explicitly approved exception to the channel
count in PLAN section 2.4. `PLAN.md` remains untouched as instructed. The
[performance options](M2-PERFORMANCE-OPTIONS.md) retain the evidence and scope;
no numerical performance gate changes.

Browsers, editors and control workflows share the primary subsystem. Admitted
file workers lease one of three data assignments, including the primary;
queued tasks do not reserve an assignment. Extra subsystems are opened lazily
and reused while the primary has a user. Per-slot weak caches and primary-only
companion ownership avoid a strong connection cycle. A rejected extra
subsystem is skipped until that authenticated connection is replaced; data
work uses the remaining assignments, serially when only the primary is usable.

The 208 request slots, 128 waiting callers and 64 remote handles are shared
across the connection. Each file pipeline also reserves 64 caller admissions,
so its window cannot silently enlarge the metadata waiting budget. Each
subsystem additionally obeys its own server-advertised handle limit. Request
IDs and file handles remain local to the subsystem that created them. Global
three-worker and 16 MiB transfer payload bounds remain unchanged.

Ordinary subsystem failure interrupts work assigned to it. Healthy data
siblings and shells continue; queued authorized tasks observe transport
liveness and may obtain a replacement subsystem on the same generation.
Old browse scopes are never rebound by that replacement. Actual transport
loss interrupts all work for the generation. Canceled tasks become visible
promptly, while their worker and data assignment remain reserved through
late-response/pipeline cleanup. Exit drains every subsystem through weak
transport references, including data clients absent from the browsing list.

## Implemented primitives

`capstan-core::sftp` contains framework-independent metadata, ownership primitives and `SftpService`. The service uses the authenticated SSH connection lease registered by the trusted terminal-start path; restricted Tauri commands forward to it. No crate depends on Tauri, and the WebView cannot create a connection by supplying credentials or a binding DTO.

## Browsing and mutation behavior

- Each page reads ahead by one supported entry, so an empty directory or an exactly full final page has `hasMore: false`. One page fill allows at most 64 protocol reads within a 15-second total deadline. Exhaustion returns a stable limit/error instead of looping indefinitely; this is not a whole-navigation or cancellation-latency guarantee.
- The service serializes directory and mutation operations per view and revalidates ownership after waiting. Navigation generations prevent an older operation from replacing a newer scope. The controller also serializes navigation IPCs, rejects stale page identity/sequence and recovers the last committed scope if a later navigation fails.
- Create is authorized only in the current successfully browsed canonical directory. A parent path from a different/previous directory, or a create before browsing, is rejected before a remote creation request. This narrows the application's browse capability, not the remote account's server permissions.
- Rename/delete/permissions use a five-minute, single-use confirmation bound to the complete owner and session. A request from another view does not consume it. A valid owner's apply consumes it before remote validation, even if validation or mutation fails; the panel closes the dialog and requires a fresh prepare for retry. Uncertain mutations are never automatically replayed.
- Explicit navigation may follow a symlink to a directory. Delete unlinks a symlink itself. Symlink permissions are rejected before confirmation because SFTP v3 SETSTAT follows the target; unknown/device types are also not offered as permission targets. Recursive deletion uses the separate bounded preview/apply contract below.
- Detach and terminal revocation cancel attached-view operations, including attach-in-progress. A transfer holds its own connection lease and survives closure of its originating shell. Normal cancellation is independently drained with request/handle/payload admission retained until convergence. Late OPEN handles receive one CLOSE. EOF, malformed state or the 15-second protocol timeout can quarantine the affected subsystem; healthy data siblings and SSH shells remain separate. Coordinated exit waits for all subsystem drainers through weak transport references. The core lifecycle matrix is extended below; abrupt network, Windows lock/exit routing and mixed-shell latency acceptance remain open.
- Transport teardown has a separate liveness token from startup cancellation, preserving trust/authentication errors. On an explicit new connection action, the production Vault path uses checked pool acquisition to retire known-dead entries and all their aliases under the map lock. Existing leases keep their original entry identity; concurrent fresh acquires coalesce. No automatic authentication, task rebinding or input replay is added. Idle expiry records its deadline at last-lease release rather than the cleanup task's first poll. Production integration covers explicit generation replacement and final SFTP lease reclamation with a simulated clock; abrupt network and desktop lock/exit/timing acceptance remain separate.
- Canceling an operation dialog prevents a late prepare response from reopening it. A successful mutation remains successful if the following refresh fails; the refresh error stays visible without inviting a duplicate mutation. Names and manually entered paths preserve leading/trailing spaces.

## Protocol adapter

The exact `russh-sftp = 3.0.1` dependency is a runtime dependency of `capstan-ssh`, used behind the bounded SFTP facade and framing adapter. Its Apache-2.0 license is compatible with the project. The resolved lockfile records the transitive packages too.

Upstream represents opaque handles as String and applies lossy UTF-8 decoding. The probe sends all 256 possible byte values. `capstan-ssh::sftp::SftpWire` compensates at the framing boundary:

1. Read a length prefix; reject zero or over 262144 bytes before allocation.
2. Encode only incoming HANDLE bytes into lowercase hex. Maximum raw handle: 256 bytes.
3. Decode only the outgoing handle fields of CLOSE/READ/WRITE/FSTAT/FSETSTAT/READDIR and the fsync/fstatvfs extensions.
4. Preserve paths, request IDs, offsets and file data. Strip incoming STATUS message/language strings before upstream parsing; diagnostics cannot echo arbitrary server text.
5. Each direction owns one bounded frame and a bounded pipe. Explicit close cancels and joins both relay tasks, including blocked readers/writers.

This adapter does not implement a request dispatcher or a second pipeline. Upstream still owns request IDs and request matching. `SftpClient` shares connection-wide admission of 208 in-flight requests plus 128 waiting callers and 64 active handles. Each subsystem additionally obeys its nonzero advertised `limits@openssh.com` max_open_handles, and closes when its u32 request-ID budget is exhausted rather than permitting wrap/reuse. The 208 ceiling reserves room for three 64-request file windows plus 16 control requests; production files use the library's existing 64-request pipeline with contiguous confirmed-prefix progress. Handle exhaustion rejects locally without quarantining the channel; CLOSE releases admission. A boundary test sets the remaining request-ID budget to zero and verifies rejection plus subsystem closure; it does not simulate billions of requests. Only extension version `1` enables `posix-rename@openssh.com` and `fsync@openssh.com`; unknown versions do not authorize mutations.

## Single-file transfer boundary

- `select_transfer_source` / `select_transfer_destination` use native Windows dialogs. Core grants are random, single use, five-minute capabilities bound to the complete Rust binding. At most 128 unused grants exist; a weak-reference reaper expires idle grants. Explicit release handles late picker responses/navigation/enqueue failures. No local path is an IPC input or output.
- `enqueue_transfer` validates the live window/terminal/SFTP binding and current browsed upload parent or regular download entry. Tasks own the authenticated connection lease independently of the view. The command group also exposes `release_transfer_selection`, `transfer_snapshot`, `cancel_transfer`, `pause_transfer`, `resume_transfer`, `retry_transfer`, `retry_transfer_on_session`, `retry_transfer_with_selection`, `resolve_transfer_conflict` and `confirm_transfer_exit`; no arbitrary local I/O, generic process or new authentication interface exists.
- `vendor/capstan-native-windows::transfer` pins ancestor handles from a local drive root, rejects reparse points and unsafe Windows names, opens a regular source denying write/delete, and holds same-directory exclusive download temporaries. Final publication/deletion uses the held file handle. Target versions include volume/file identity, size, FILETIME and attributes; equal size/mtime with a different file identity is rejected. UNC/device/verbatim paths, paths over 32767 UTF-16 units, more than 64 components and unsupported basenames fail closed.
- The core streams at most 32 KiB per request using the selected library's 64-request pipeline. Opaque payload guards retain the frozen 16 MiB admission through canceled-pipeline convergence and CLOSE. Uploads use exclusive `.capstan-<UUID>.partial` files in the remote parent with mode 0600; after FSTAT, optional advertised fsync and close, core reads back the complete SHA-256 and checks attributes again. Downloads check lstat/FSTAT baselines, accept short reads, verify EOF, sync a native temporary and read it back for SHA-256 before publication. Existing mode/timestamps are not preserved automatically on upload replacement; chmod remains explicit.
- Existing targets require a revision-bound replace/save-as/skip decision. Decisions are single use and rechecked after waiting and before publication. Final target checks/publication are serialized across app tasks by a global commit gate, including aliases of local targets; staging remains concurrent. The gate is released before waiting for user decisions. External clients can still race between stat and rename; SFTP size/mtime/type equality is not a content identity or CAS guarantee.
- Remote replacement requires advertised `posix-rename@openssh.com`; absent support offers save-as/skip, never delete-before-rename. An uncertain rename is not replayed. A fresh SFTP channel on the same authenticated SSH transport may prove completion through temporary-name absence, formal-target baseline and full readback hash plus post-read attributes. Otherwise the task fails with cleanup required. This read-only reconciliation is not automatic reconnection or resume.
- Snapshots expose only bounded metadata, canonical decimal u64 values, monotonic task versions, stable errors, conflicts and cleanup state. `fixtures/M2-transfer.json` is consumed in Rust/TS. Queue rows retain order. Progress advances on confirmed bytes and is exact on entering verification; speed starts at the running phase after queue/initial user waits. UI polls serialized snapshots every 250 ms; core throttles progress changes to 100 ms.
- A commit already admitted cannot be canceled. Exit blocks new work and drains cancellation for up to 30 seconds; failure keeps the window alive. Default Vault lock keeps authorized jobs running; disconnect-on-lock clears grants/cancels jobs before connection teardown. A blocked native disk operation can exceed the proposed cancellation SLA.
- The assigned data subsystem's read-only close notification wakes its active admission, conflict decisions and final-publication gate waits, without acquiring a request slot or canceling an admitted native commit. Subsystem loss reports `interrupted` / `connection_lost`; uncertain remote mutation cleanup remains explicit. Native blocking I/O is awaited rather than dropped. EOF/quarantine does not replay an admitted request. Queued authorized tasks observe the SSH transport lifetime and may acquire a fresh subsystem on the same authenticated generation; interrupted active tasks still need explicit retry.
- Healthy upload failures capture FSTAT through the owned handle before close and compare the temporary's lstat before removal. Changed/uncheckable temporaries and disconnected/uncertain results retain a cleanup-required flag; missing temporaries and known rejected exclusive OPEN requests do not. SFTP v3 has no atomic compare-and-delete: equal-attribute replacements and the check-to-remove gap remain possible.

### Folder batch conflicts

- Native upload-folder selections and Rust-owned download trees now capture every destination version before queue admission. A random batch ID is created in core for that one selection, with bounded `{id,name,files,conflicts}` metadata in snapshots. No command accepts a batch ID as authority or joins caller-supplied task IDs into a group. Upload grants additionally bind the exact tree target. Product folder pickers and OS drops now use at most eight five-minute reviewed plans and atomic file-task admission up to the remaining 1024-task limit, without per-file IPC grants. The internal source-grant helper retains its existing 128-grant bound. Enumeration remains bounded at 4096 entries/64 levels; exceeding an admission limit fails explicitly, not as a complete transfer.
- `resolve_transfer_conflict` adds `replace_batch` and `skip_batch` alongside the existing individual decisions. The originating window, task ID and exact displayed revision must match a live conflict with `batchEligible: true`. The policy is single-use for that batch and wakes both currently waiting members and later queued members. There is no application-wide default and editors never inherit it.
- Group eligibility is confined to previously existing regular destinations whose current version still equals their own preflight snapshot. Appeared, disappeared or changed targets require an individual decision, as do another change before publication, a renamed destination and every explicit retry. Remote snapshots compare type/size/mtime/permissions; Windows versions also compare volume/file identity and FILETIME. The final publication gate and native commit checks are unchanged; this is not server-side CAS or a whole-directory transaction.
- Independent preflight snapshots run in groups of at most sixteen through the existing request/native admission, retaining input-to-version association regardless of completion order. This metadata window uses the existing request headroom; file workers remain three, SFTP subsystems remain at most three, and request/handle/payload ceilings do not increase. The whole native group is awaited on a peer error before returning; no grant/task is published from a failed preflight and the next group is not started. Tree scans schedule ancestors before descendants, overlap only peers at the same depth and preserve original conflict entry/order. A conflicting/invalid directory still prevents every preflight lookup beneath it. These snapshots remain per-target observations, not a whole-tree transaction; final version/parent checks and the global publication gate remain authoritative.
- An existing upload-tree parent is canonicalized before bounded read-only ancestor type snapshots are joined. Every ancestor must still be a directory before staging/publication. Missing ancestors use the original ordered LSTAT/MKDIR sequence followed by a final canonical-path check. Failed snapshots join the admitted group and prevent publication. All final snapshots remain inside the original global publication gate; verified temporary, target-version and complete-hash checks are unchanged. External replacement between observations and rename remains the documented SFTP v3 race.
- The bilingual dialog defaults to individual actions. Explicit batch consent is keyed to the current task/revision/batch, clears on a new prompt, and changes the replace/skip action labels. Save-as stays individual. Missing atomic replacement disables batch overwrite while keeping skip/save-as available. Existing directories are merged; incompatible tree components and Windows-inexpressible names still fail closed rather than being silently overwritten or renamed.
- The folder downloader now prefixes every file/subdirectory with the selected root name, including empty directories. Production russh/native tests cover root preservation, nested files, queued identity changes, both batch policies, stale/cross-window/foreign-target rejection and retry isolation. Actual Explorer drag and affected GUI acceptance remain separate.

### Partial continuation and explicit retry

- An interrupted upload may retain its owned remote `.capstan-*.partial` path; an interrupted download may retain its native local partial and exact size. The task never guesses an offset from an unverified file.
- `open_existing_file` and `seek_to` reopen/position the stream only after owner/session validation. Before appending, the core reads and compares the completed prefix against the newly selected local source or current remote formal target. A changed source, replaced partial, invalid partial name, or inconsistent local size fails closed as `resume_mismatch`/`target_conflict`.
- Retrying an interrupted task requires a fresh SFTP session and, for uploads, a new owner-bound local selection token. The previous native source handle is released when the transport is lost. A successful commit removes the partial; uncertain or changed cleanup remains visible and is never auto-deleted by startup code.
- Core continuation remains separate from a persisted task queue. A bounded two-slot ledger now records known transfer partials after a crash and supports explicit remote-upload resume/cleanup after reconnect and a fresh picker; it does not replay queued tasks; new download records can reattach only through a fresh exact-target picker and their saved native file identity. Recursive folder download/upload preserves bounded directory trees, including empty directories, through native picker capabilities. Regular-file batch decisions are defined above; directory/name/type preflight decisions, native drag/export and identity-checked local-download reattachment are now implemented; affected GUI acceptance and the fixed full performance/candidate gates remain B work.

## Panel preferences and settings exit contract

`load_sftp_panel_preferences` returns only `{layout: {dock, size, collapsed}, session, sequence}`. `save_sftp_panel_preferences` accepts the same metadata, with an exact decimal-u64 sequence greater than zero. Both require the main window. The runtime session is not a local-path capability. Dock is `right|bottom`, size is an integer 20–60, and unknown layout fields are rejected. Existing tabs retain independent ephemeral layouts; a change updates the saved default for future SSH tabs and restarts. Initialization/old responses cannot replace a newer dirty choice.

Rust selects `settings.json` under the already resolved application data root. The document is at most 16 KiB, has schema version 1, and adds the `sftpPanel` field while preserving unrelated settings, including the separately native-selected `remoteEditor` preference. Invalid known fields, malformed/oversized data, unsupported schema versions and reparse/unsafe local paths fail closed. Atomic publication uses existing held native destination/temp handles and identity rechecks. There are at most 32 admitted writes; runtime sequence ordering prevents stale writes. Pending blocking work retains admission even after a dropped caller. The exit coordinator concurrently stops/drains settings writes and transfer work under the 30-second bound. Failure keeps the window open and restores admission; it does not replay canceled jobs or prove an uninterruptible disk call finished within the deadline. Panel preferences add no host, remote/local file path, tab ID, alias, body or secret. The remote-editor feature additionally persists only the explicitly native-selected local executable path in Rust.

Load/save errors retain the current-session layout and expose bilingual retry. Retrying reloads the storage baseline without discarding a dirty local selection. Changed/corrupt files are preserved, with no automatic reset. Native restart/error interactions remain an affected manual increment, separate from earlier A acceptance.

## Managed shell-block planner prerequisite

`shell_integration::plan` accepts Rust-owned UTF-8 configuration bytes, Bash/Zsh,
install/uninstall and an authenticated target. Configuration and replacement are
bounded at 64 KiB; `Plan` deliberately has no serialization implementation. A
versioned application marker, exact generated-block recognition, reserved-name
collision checks and original-prefix hashing protect byte-preserving repeat
install/uninstall. Unknown or edited blocks fail closed. Insertion into a file
without a trailing LF records ownership of that separator; changed prefix bytes
then require manual repair before uninstall. This conservative refusal avoids
joining unrelated user text. Existing supported hooks and command status are
preserved; read-only/unsupported hook containers remain unchanged.

The generated hooks are bounded OSC 7 producers, not authentication or file
capabilities. They use the validated target, never a shell-provided hostname.
Four planner tests and 16 actual local WSL PTY cases cover the generated bytes;
the conditional exporter test alone is not shell execution. The application now
has a bound preview/apply command pair: it rereads the selected remote file,
consumes a single-use owner/generation/expiry-bound token, keeps replacement and
backup bytes in Rust, preserves permissions and uses atomic replace when
advertised. Complete installer lifecycle, residual handling and real remote
install/uninstall acceptance remain open; the local planner/PTY evidence alone
does not close those items.

## Cwd and editor input contract

`sftp::cwd::CwdAuthority` validates only `file://authority/absolute/path`. The authenticated target and up to eight explicitly bound aliases are normalized as ASCII DNS names or IP literals; IPv6 URI literals require brackets. Empty/localhost, short-name/FQDN and resolved-DNS equivalence are never inferred. Userinfo, ports, query/fragment, malformed escapes/UTF-8, controls and oversize input fail closed. Decode exactly once, retaining literal encoded percent signs and POSIX dot segments for SFTP realpath. The shared [hostile fixture](fixtures/M2-cwd.json) includes cross-host, encoded Unicode/control, one-decode and IPv6 cases. Parsing grants no local access or write/exec authority.

`update_remote_cwd` takes the source terminal, current SFTP capability, exact connection generation/sequence and bounded URI. Rust derives the target from the authenticated lease and keeps the last valid hint separately from directory scopes. Duplicate/older sequences cannot replace it; invalid hints preserve it. `configure_remote_cwd_aliases` uses the same binding; null reads current state, a bounded explicit list replaces aliases and revalidates/revokes cached hints. Both return only `{sequence, path, aliases}` metadata. Source closure clears UI hints; reattachment/configuration epochs reject stale responses. The 250 ms hub and serialized/coalesced validation avoid per-output IPC floods. Manual directory navigation disables Follow; Refresh preserves it; hidden/collapsed tabs and pickers/confirmations/mutations defer auto-navigation. Existing SFTP realpath/list validation preserves the previous directory on failure. Bash/Zsh preview/apply is wired through the managed transaction path; full install/uninstall lifecycle acceptance remains open.

The editor B contract supports regular text files up to 8 MiB: valid UTF-8 with optional BOM, or valid BOM-marked UTF-16 LE/BE, rejecting NUL/control characters except tab/CR/LF. Detection is Rust-only and preserves encoding/newline bytes; no body enters WebView. A native-selected absolute `.exe` is saved as the private `remoteEditor` preference in the bounded `settings.json`; IPC returns a process-local configuration ID. Controlled absolute document paths are separate argv entries, never shell text. The core watcher observes every 500 ms, requires an unchanged fingerprint/content for 1000 ms, ignores unchanged committed bytes and serializes each session. A missing/sharing-locked file during rename-save resets stability. Child-process exit never closes a session.

`begin_remote_edit` takes terminal/session/entry/configuration IDs. `remote_editor_configuration`, `select_remote_editor`, `remote_edit_snapshot`, `retry_remote_edit`, `cleanup_remote_edit_temporaries`, `resolve_remote_edit_conflict`, `close_remote_edit` and `discover_remote_edit_residuals` require the main window. Snapshot metadata and exact revisions are frozen by [M2-editor.json](fixtures/M2-editor.json). It contains bounded session IDs, name, optional remote path/host, state, dirty/recovered/cleanup flags, replace availability, at most eight remote temporary records `{id,path,state}` per edit and stable error codes, without document bytes, editor paths or staged local paths. The global UI survives source-panel/terminal removal. Upload observation and network work run in Rust even when the UI is hidden.

Editing captures remote attributes and SHA-256, verifies the staged temporary by full readback, preserves existing permission bits, then shares the transfer service's final validation/publication gate and atomic commit primitive. The target's parent, type, size, mtime, permissions and SHA-256 are checked again before rename. Baseline/conflict inspection compares bounded raw bytes, so a concurrent binary replacement still requires a conflict decision. Explicit replacement is bound to the remote version observed at conflict; another change requires another decision. No-atomic-replace targets allow a new absent name. SFTP still has no CAS rename, so the external-writer race between the final check and publication remains.

Local staging is protected for the current Windows user and SYSTEM. A versioned basename-only marker and exclusive ownership handle support startup discovery without storing a plaintext host/path recovery list. Recovered copies have no upload authority and can be exported, retained or explicitly discarded; they are never uploaded automatically. Discovery is bounded to eight owned sessions / 256 inspected roots; invalid, unknown and live-instance trees are retained. Canceling the native export picker returns `false` and keeps the session. Cleanup happens only after local copy publication or explicit discard; failure keeps the session visible. Open editors block exit until resolved; settings/transfer drain failures reopen editor admission. Disconnect-on-lock cancels the editor token and retains its local copy. Explicit retry can bind an edit ID to a current authenticated terminal/SFTP pair. Core requires the same host and full pool policy (credential revision, pinned trust, user/target, Agent and proxy included), permitting only a changed Vault epoch after explicit authentication. The original attributes/hash remain the publication baseline. Startup copies retain only a cleanup policy and cannot bind for document upload or remote replay.

## Current native/tree/recovery command extension (2026-10-19)

- `arm_native_drop` validates the current SFTP upload parent and records a Rust binding/parent/target lease. Only a real native drop registers paths. `enqueue_native_drop` consumes a 60-second receipt only for that same armed lease, complete connection generation/terminal/window binding and parent. Disarming is token-conditional, UI arm/disarm IPCs are serialized, and window/lock teardown revokes receipts. Switching tabs or receiving a late event cannot redirect the old source into a new target. The custom event contains only a receipt UUID and logical coordinates; built-in Tauri native-drop metadata is not accepted as I/O authority.
- Folder pickers use `select_transfer_folder_plan` / `select_transfer_folder_download_plan`, followed by `resolve_transfer_tree_plan` or `release_transfer_tree_plan`. The legacy immediate-create folder commands are no longer registered. `fixtures/M2-tree.json` is shared by Rust/TS and includes an exact revision above 2^53. Choices refer only to Rust node IDs and basenames, never local paths or caller-created trees. Merge requires the exact current directory version; rename propagates to descendants and skip covers the subtree. Whole-tree publication/rollback is not promised.
- `prepare_native_export` returns an export token plus the same reviewed basename plan, including single files with Windows-invalid names. After all decisions, the engine stages known files and directories; `native_export_snapshot` reports bounded planning/preparing/ready/dragging/retained/failed metadata. `start_native_export` revalidates the live binding and invokes copy-only OLE on the native main thread. Returning from OLE, Escape, expiry and process exit preserve staging. `release_native_export` requires explicit copy-finished consent and waits/cancels owned file tasks. Exclusive cleanup handles reject active readers; markers enumerate exact D/F/P entries and no unknown partial is adopted. Recovered stages have local cleanup authority only.
- New transfer ledger entries store a Rust-only Windows volume/file identity. `select_recovered_transfer_destination` requires a fresh native save picker selecting exactly the recorded target, rejects replaced/reparse/hard-linked partials and pins the file exclusively. `retry_recovered_transfer_download` checks the full remote prefix before continuation; `cleanup_recovered_transfer_download` consumes the same reauthorized destination grant and removes only its held partial. Releasing an unused grant preserves that partial. Legacy records without identity remain manual-inspection cases. Empty-file intents are valid; upload intent is saved before OPEN.
- Shell apply now uses the shared hash-verified atomic publication gate, private backup and mode-preserving replacement. A repeat/no-op creates no backup or write. Uninstall preserves appended user commands and a necessary newline boundary. Config bodies and backup bodies remain Rust-only; preview exposes bounded metadata. Modified blocks, stale previews, encoding/type/size errors and publication failures preserve the original file.

Retry completion releases the old SFTP client/SSH lease. A fresh retry must match the original host, remote path, target and full authenticated pool policy; only a new Vault epoch is permitted. Validation and local-capability admission happen before changing the final queue state. Uploads require a new source; interrupted downloads may retain the original destination capability. Failed prefix verification preserves the partial and recovery record. Explicit successful retry reopens the final UI row; unsolicited stale snapshots cannot. Current-process task IDs are excluded from the startup-recovery list.

The 2026-10-20 continuation corrects live download reauthorization: `retry_transfer_on_session` resolves the original Rust-recorded path through an opaque task descriptor instead of looking up an old `RemoteEntryId` in a fresh browse scope. It restats the source through the current authenticated client and matches the original regular-file type, size, mtime and permission baseline as well as the complete retry policy. Failure leaves the terminal task revision, destination and partial unchanged. New recovery records persist that source baseline as Rust-only `sourceBaseline`; the public recovery DTO does not expose it. Older records remain discoverable but cannot continue without the original source baseline or saved native identity. Preserve those records for manual inspection rather than inventing a baseline from current remote content. Full prefix verification and final hashing remain required after successful reauthorization.

New persistent records also carry Rust-only `policySha256`, a domain-separated digest of the original authenticated pool policy. Its length-prefixed strings and fixed-width fields include endpoint, port, username, credential ID/revision, trusted fingerprint, Agent identity/forwarding and proxy policy; only the Vault epoch is excluded to permit explicit reauthentication after unlocking. Recovered upload continuation, remote partial cleanup and native download reattachment require the saved digest to match the current lease before consuming a new picker capability or changing the task. No plaintext credential or serialized `PoolKey` is added to the ledger or public DTO. Legacy records without this digest remain visible for manual inspection and cannot inherit the current authentication policy. In-process tests cover every included policy field, the permitted epoch change, persisted changed-credential rejection and original source-metadata rejection without altering the retained bytes.

Transfer recovery storage now seals the complete frame with current-user Windows DPAPI, without machine-wide protection or prompts. The two exclusively held, non-reparse, single-link slot files live beneath a restricted, pinned directory. Additional entropy binds its volume/file identity and the slot index, rejecting ciphertext copied to a different directory or slot. Plain frames are bounded to 256 KiB / 128 records; sealed files to 288 KiB. Serialization and decrypted byte buffers are zeroized. The inner versioned SHA-256 frame detects accidental damage; DPAPI supplies the profile-bound authenticated envelope. This protects stored metadata independently of the Vault password, and does not defend against arbitrary code running as the same Windows user. Platforms without this native boundary fail closed rather than write plaintext.

Decodable legacy plaintext frames are treated as untrusted descriptors: their saved policy proof is removed before the selected records are encrypted and synced into both slots. Encryption never upgrades old records to continuation or cleanup authority. Undecodable bytes and user partials are preserved for inspection. Startup selects the newest valid frame, exposes incomplete discovery after unreadable slots, and persists that warning through later updates. If both slots are unreadable, it neither scans partial filenames nor invents records. Process exit releases held files without requiring Rust destructors; discovery after restart still needs fresh authenticated context and picker grants for any mutation. This is bounded residual discovery, not queue restoration or a power-loss guarantee. Losing the Windows profile keys or copying the ledger to a new directory identity can make recovery metadata unreadable; keep the partial data for manual inspection.

The bounded public recovery state includes `manual_inspection` when a present
candidate lacks original policy, download-source baseline or native identity.

The closeout correction distinguishes resumable interruption from failed
cleanup. A verified owned partial whose removal fails is persisted with

regular-file size/modification/permission baseline; download cleanup requires

## Recursive remote deletion contract (2026-10-20)

- `prepare_remote_tree_delete` accepts only a Rust-owned directory entry in the current authenticated SFTP view. Core rescans the directory with `lstat`, refuses unknown/device types, follows no symlink, and verifies directory `realpath` identity. The preview is bounded to 4096 entries, 64 levels and 256 KiB of path bytes; it returns only a random five-minute token, host/path metadata and file/directory/symlink counts.
- `apply_remote_tree_delete` is bound to the same window, terminal, SFTP session and preview token. Before mutation it rescans and compares the complete ordered metadata snapshot, so any entry appearance, removal, type, size, mtime, permissions or canonical-directory change requires a new preview. The token is single use and is removed after the report, including a failed or canceled apply.
- Deletion is depth-first: regular files and symlinks use unlink, directories use `rmdir`, and ancestor directory type/permissions/realpath are rechecked before each admitted request. A symlink is removed as a link and is never traversed. Each entry returns `removed`, `failed` or `retained` with a stable error; a failed child retains its ancestors and later cancellation retains items that were not admitted.
- `cancel_remote_tree_delete` stops admission of later entries. An unlink/rmdir already admitted uses an independent cancellation token and waits for its real protocol acknowledgement before reporting the item as removed or failed. Exit marks the window closing, cancels future plans and drains tree deletion, transfers and settings concurrently in the core coordinator under the existing 30-second budget. Failure restores all three admissions and keeps the window open; it does not replay canceled work. Both explicit exit and native window-close routing use this coordinator.
- The frontend receives only bounded metadata and validates paths, UUIDs, counts, outcomes and error codes. It displays a bilingual summary/result dialog and paginates reports at 50 entries. Tree deletion is intentionally separate from the single-entry confirmation because the preview and partial-result semantics differ; whole-tree deletion remains non-atomic on SFTP v3.
