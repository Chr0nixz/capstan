## 发现

### C1 · P1：广播多行确认遗漏 CR

位置：`ui/src/panes/contracts.ts:26`。

`/\r?\n/` 只识别 LF/CRLF。输入 `one\rtwo` 时，两个目标均被选中，但 `requiresConfirmation=false`。终端将 CR 解释为回车，后续使用该路由接入广播时会漏掉多行确认。现有单窗格策略 `terminal/security.ts:25` 已使用 `/[\r\n]/`，两者不一致。

在仓库根目录执行（Node 22.23.2、PowerShell）：

```powershell
node --experimental-strip-types --input-type=module -e 'import { routeInput } from "./ui/src/panes/contracts.ts"; console.log(routeInput("a", ["a", "b"], true, "one\rtwo"));'
```

实际：`targetPaneIds: ['a', 'b'], requiresConfirmation: false, blockedReason: null`。预期：对含 CR 的多行广播输入要求确认。应补 CR、LF、CRLF 和 bracketed paste 内容的用例，并在 M3-1 接线时覆盖确认前零投递。

### C2 · P2：同代次允许重连直接回到在线

位置：`crates/capstan-ssh/src/connection_state.rs:150`、`ui/src/connections/contracts.ts:53`。

输入同一 `connectionId` 的 `generation=8, reconnecting, connection_lost`，随后输入 `generation=8, online, null`，Rust `validate_successor` 和 TS `acceptsConnectionSnapshot` 均返回成功。旧连接的迟到 online 快照可因此清除重连状态。PLAN §2.4 和 M3 不变量要求实际重连建立新连接代次；仅要求“较大代次从 connecting 开始”未封住这条同代次路径。

复现：运行下文公共探针，实际两端均输出 `same_generation_reconnect_online true`。预期：重连成功走更大代次的 connecting/认证/online；若要表达“原连接探测后仍在线”，应先明确它与实际重连的状态含义，不自行改变方案。

### C3 · P2：判别字段通过字符串强制转换绕过类型校验

位置：`ui/src/connections/contracts.ts:32`、`ui/src/forwarding/contracts.ts:74`、`ui/src/commands/contracts.ts:58`。

这些位置检查 `String(value)`，返回时却保留原始值。JSON 数组 `['online']`、`['running']`、`['forwarding']` 被接受为声明为字符串的状态或面板字段。后续严格比较、switch 和动作分发不再符合 TypeScript 类型保证。

复现：运行公共探针。实际 TS 分别输出 `connection_array_state ["online"]`、`tunnel_array_state ["running"]`、`command_array_panel ["forwarding"]`；Rust 拒绝前两个快照。预期：解码器拒绝非字符串判别值，并覆盖 JSON 数组等负例。

### C4 · P2：片段长度按 UTF-16 与 UTF-8 分别计数

位置：`ui/src/snippets/contracts.ts:19`、`crates/capstan-vault/src/model.rs:347`。

TS 使用 `string.length`，Rust 使用 UTF-8 `str.len()`。同一份片段在 UI 校验通过，Rust 校验失败；接入保存后会影响中文和 emoji 内容。

复现：运行公共探针；各输入均保留 fixture 的合法 ID 和分组引用。

| 输入 | TS 实际 | Rust 实际 |
| --- | --- | --- |
| 名称为 100 个“中”（300 UTF-8 字节，限额 256） | 接受 | 拒绝 |
| 模板为 3000 个“中”（9000 字节，限额 8192） | 接受 | 拒绝 |
| 分组名为 50 个“中”（150 字节，限额 128） | 接受 | 拒绝 |

预期：在契约中明确单位并统一校验。现有测试仅用 ASCII 越界值，无法发现此差异。

### C5 · P2：其他跨层校验范围仍不一致

位置：`ui/src/forwarding/contracts.ts:34,76`、`ui/src/connections/contracts.ts:28`；对应 Rust 为 `TunnelConfig::validate`、`TunnelRuntimeSnapshot.active_connections: u32` 和 `validate_snapshot`。

复现：运行公共探针。

| 输入 | TS 实际 | Rust 实际 |
| --- | --- | --- |
| `active_connections=4294967296` | 接受 | u32 反序列化拒绝 |
| 隧道 `destination_host='bad/host'` | 接受 | 配置校验拒绝 |
| 连接 ID 为全零 UUID，代次仍合法 | 接受 | 快照校验拒绝 |

预期：对共同边界采用一致的整数上限、地址和身份校验，并让 Rust/TS 共同读取负例。当前共享 fixture 主要证明合法值往返，B 报告“非法地址、越界计数拒绝处理”的结论过宽。这些问题尚不构成 Rust 校验绕过。

### C6 · P2：M3-0 代码前审查记录不完整

依据：`M3.md:27,36`。本阶段要求核对 russh 转发能力、Windows 唤醒/网络事件入口，并固定命令/事件名、取消所有权和测试范围。

预期：先补简短契约表和能力核对，明确连接/窗格/隧道取消的 owner、任务回收、锁库策略与部分失败行为，再进入依赖阶段。此项不要求提前实现 M3-1 至 M3-4 运行时，也不授权修改 PLAN、vendor 或权限配置。
