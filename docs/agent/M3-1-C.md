## C1 · P1：聚焦窗格的协议回复误入广播（已关闭）

位置：`ui/src/terminal/TerminalPane.tsx:159–164`；事件入口为 `ui/src/terminal/session.ts:223–230`。

首审时 `terminal.onData` 同时接收用户输入和 xterm 自动生成的协议回复。`captureInput` 仅凭当前标签、广播开关和焦点判断是否广播，导致聚焦窗格收到 DSR 光标位置查询 `ESC[6n` 时，回复 `ESC[row;colR` 会广播或丢弃。

当前实现新增 `subscribeTerminalInput`，利用 xterm 5.4 同步 dispatcher 的 `wasUserInput` 标记区分来源。仅用户来源进入可广播输入队列；协议来源走独立 `sendProtocolInput`，固定发回自身 pane 的目的 FIFO，不等待广播确认。来源未知时关闭受管 pane 的输入队列并报告稳定错误，避免按焦点猜测路由。版本相关接线集中在 `ui/src/panes/xtermInput.ts`，没有修改总体架构。

## 错误路径与边界

- 现有测试通过：确认前/取消零投递、CR/LF/bracketed paste、空集合、目标去重、64 KiB 上限、并发 FIFO、部分失败/未知结果无重放、路由与端点 owner 固定、重启隔离、关闭目标后准确报错。
- 独立新增检查通过：来源窗格在确认期间关闭后，即使继续确认也没有目标收到输入。
- 另观察到：输入已进入目标 FIFO 后关闭来源，不会撤回目标中已接受的数据；阻塞目标首笔 `hold`，排入 `late`，关闭来源再放行，实际收到 `["hold","late"]`。按 M3-0 的“队列已接受”语义，不另计为重放缺陷；B 的“来源失效时零投递”应限定为进入目标队列前，不能理解为撤回已接受输入。
- 嵌套/合并保留终端实例、标签重排不重启会话、关闭单窗格、隐藏 renderer 和焦点 SFTP 绑定的现有单元/组件检查通过。原生显卡、IME 和实际 SSH/SFTP 日常流程仍需手测。
