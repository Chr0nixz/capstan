## C1 · P2：恢复 Vault 备份后仍禁止 SSH 连接

位置：`crates/capstan-core/src/lib.rs:1350`（`restore_recovery_candidate`）、`:744`（连接入口）。

锁库把 `connections.locked` 设为 true；普通解锁会清除此标记，备份恢复成功分支却遗漏了它。恢复后的 Vault 可读取主机、状态为已解锁，所有新 SSH 启动仍被连接入口拒绝。Tauri 的 `attempts.allow_new()` 只清除另一层标记，不能修复 Core 状态。

探针 `review_restoring_a_vault_backup_reenables_ssh`：保存含主机的备份 → 锁库 → 列举并恢复备份 → 连接已恢复主机。实际：

```text
restored unlocked=true hosts=1 SSH error=Some("vault_locked")
```

预期恢复成功后可正常连接；应补齐与普通解锁一致的恢复出口及 SSH 回归测试。重新锁库再普通解锁可绕过此问题，现有 Vault 恢复测试只验证数据可读，未检查后续连接。

## C2 · P2：主动退出的 SSH 窗格被共享连接重连重新启动

位置：`ui/src/connections/controller.ts:51`、`:57`、`:77`；后端正常退出释放 owner 位于 `src-tauri/src/lib.rs:677`。

终端收到 `exited` 后仍保留连接订阅；后续较大代次的 online 不区分自然退出与断线结束，一律创建新 shell。同一连接还有其他活跃窗格时，已输入 `exit` 的窗格也会被重新打开。

手动触发流程：同主机打开两个窗格 → 第一个输入 `exit` 并保留结束画面 → 第二个经历断网/恢复。独立控制器探针 `review: an exited SSH pane must not auto-open a shell when another pane reconnects` 注入同样的终端/连接状态，实际启动次数由 1 变为 2，第二次携带 `expectedGeneration: '2'`。

预期已主动结束的 pane 保持终态，只有用户显式重新连接才开新 shell。应按终端结束原因保留恢复资格，并补共享连接中部分 shell 正常退出的测试。

## C3 · P2：迟到的重连命令响应覆盖已在线状态

位置：`ui/src/connections/controller.ts:57–64`、`:128–130`。

事件经过 feed 的迁移校验，但 `reconnect()` 将命令返回的 connecting 快照直接交给 `receive()`；后者只比较 session 代次下界，不检查同代次状态迁移。若新代次 online 事件及 shell 启动先到、命令响应后到，状态会退回 connecting，关闭输入且没有后续 online 事件解除挂起。

探针 `review: a late reconnect command reply must not suspend the new online session` 延迟命令 Promise，在新 shell 启动后交付同代次 connecting 响应。实际：

```text
late reconnect reply { ended: true, state: 'connecting' }
expected { ended: false, state: 'online' }
```

这是可控 IPC 时序反例，未声称在原生 WebView2 中测得其发生频率。预期命令响应也遵守已接受快照的迁移规则，拒绝该倒退；应补事件与命令响应交错测试。

## C4 · P2：取消单个尝试等待了其他 owner 的长期监控任务

位置：`crates/capstan-core/src/lib.rs:855–871`（`cancel_connection_attempt`）。

匹配 attempt 后取消 operation、等待 gate，然后对整个 entry 的 TaskTracker 执行 wait。等待期间另一个 owner 可以成功建立新代次并启动长期 monitor；该 monitor 也进入同一个 tracker，导致取消调用等待其整个生命周期，而非仅等待被取消尝试。

探针 `review_cancel_attempt_does_not_wait_for_a_surviving_owner_monitor`：暂停首个 owner 的认证 → 第二个 owner 加入并等待 gate → 取消首个 attempt → 允许第二个认证成功。实际：

```text
cancel completed=false original_error=Some("canceled") survivor_connected=true completed_after_last_owner_release=true
```

取消在 3 秒内没有返回；释放最后一个 owner 后立即结束，确认等待的是存活 monitor。预期首个尝试回收完成即可返回，存活 owner 继续工作；等待范围应绑定被取消的尝试/代次。

此项在真实进程内 SSH 服务端的 Core API 并发调用中确认。Tauri 初始启动取消另有前置等待，本轮未在原生交互中复现相同时序，不把该探针等同于桌面复现。

## C5 · P3：SFTP 使用说明仍描述旧的手动恢复流程

`docs/SFTP.md:34` 要求断网后先显式重连，再选择“重试”；当前 supervisor 会自动重连并重绑持有授权的中断下载。应同步说明自动恢复的适用范围、再次覆盖确认，以及上传/进程重启仍需显式选择。无需改变既定 M3 架构。
